== About This Workshop

Traditional database authentication relies on static passwords stored in Kubernetes Secrets, configuration files, or centralized vaults. These credentials present persistent security risks:

- **Credential theft** enables unauthorized access long after a breach
- **Password sharing** makes it impossible to audit who actually connected
- **Manual rotation** is error-prone and rarely happens on schedule
- **Network-only security** fails to verify workload identity

This hands-on workshop demonstrates **Zero Trust Workload Identity** using SPIFFE (Secure Production Identity Framework for Everyone) and the Zero Trust Workload Identity Manager (ZTWIM). You'll eliminate database passwords entirely by establishing mutual TLS (mTLS) connections authenticated with short-lived X.509 certificates bound to each workload's Kubernetes identity.

== Understanding Zero Trust Concepts

Before diving into the hands-on lab, let's understand the key concepts:

=== Traditional Database Authentication Problems

**Static Credentials:**

* Passwords stored in Kubernetes Secrets, environment variables, or configuration files
* Credentials persist indefinitely unless manually rotated
* If leaked, attackers have persistent access
* Hard to audit who actually used the credential

**Network-Only Security:**

* Traditional approach: "if you're on the network, you can connect"
* Zero trust principle: "never trust, always verify"
* Network position doesn't prove workload identity

=== SPIFFE & SPIRE

**SPIFFE (Secure Production Identity Framework for Everyone):**

* Open standard for workload identity
* Uses X.509 certificates with short lifespans (default: 1 hour)
* SPIFFE ID format: `spiffe://trust-domain/path/to/workload`
* Workload identity is cryptographically verifiable

**SPIRE (SPIFFE Runtime Environment):**

* Implementation of the SPIFFE specification
* Automatically issues and rotates certificates
* Workload attestation based on Kubernetes service accounts
* No manual certificate management required

=== How ZTWIM Works

1. **Workload Registration:** Each pod gets a unique SPIFFE ID based on its Kubernetes identity (namespace + service account)
2. **Automatic Certificate Issuance:** SPIRE issues short-lived X.509 certificates to authenticated workloads
3. **Mutual TLS (mTLS):** Both client and server present certificates to prove identity
4. **Automatic Rotation:** Certificates are renewed before expiration without downtime
5. **No Passwords:** Database authentication uses certificate CN matching instead of passwords
